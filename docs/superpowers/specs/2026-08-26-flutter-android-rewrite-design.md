# LifeRPG — Flutter / Android Rewrite

**Date:** 2026-08-26
**Status:** Approved design, not yet implemented

## Goal

Replace the React web app with a Flutter application that builds to a native
Android package. The Flutter app is the only client; the React app and its
Firebase Hosting deploys are retired at cutover.

The Firebase project (`liferpg-f3bab`), the Firestore data model, and the
Firestore security rules stay as they are, apart from one deliberate rule
addition described under "First-login bootstrap".

## Decisions

| Decision | Choice |
| --- | --- |
| Scope | Android only. React web is deleted. |
| Repo | Same repo, replaced in place. History preserved. |
| Visual target | Faithful parchment/heraldic theme, native mobile interaction patterns. |
| Data layer | Live Firestore snapshot streams with on-device offline persistence. |
| State management | Riverpod, over a repository layer. |
| Application id | `com.liferpg.app`, minSdk 23. |

Rejected: BLoC (ceremony out of proportion to three screens); plain
`StreamBuilder` with `InheritedWidget` (hand-rolls what Riverpod provides and
forces constructor injection of Firebase throughout the tests); clean-slate
Material 3 (discards the app's visual identity).

Fonts are bundled as assets rather than fetched at runtime through the
`google_fonts` package: the app must render correctly on a cold, offline start,
which is the point of choosing offline persistence.

## Auth

Sign-in uses `google_sign_in` for the native Android account picker, exchanging
the Google ID token for a Firebase credential via `signInWithCredential`.

Two prerequisites live outside the code and are the most likely source of
first-run failures:

- the debug **and** release SHA-1/SHA-256 fingerprints must be registered on the
  Android app in the Firebase console;
- `android/app/google-services.json` must be downloaded from that app. It is
  gitignored and supplied to CI as a repository secret.

`authStateProvider` wraps `FirebaseAuth.authStateChanges()`. `appUserProvider`
watches `users/{uid}` and yields the `AppUser` (including `admin` and
`readOnlyOthers`). An unauthenticated state routes to the login screen; this
replaces the imperative `navigate("/login")` in `useAuth`.

Routing uses the plain `Navigator` rather than a routing package. `LifeRpgApp`
watches `authStateProvider` and shows either `LoginScreen` or `HomeScreen` as
its home; the edit and user-management screens are pushed with
`Navigator.push`. There are no deep links or URLs to model, so `go_router`
would earn nothing here.

### First-login bootstrap

The web app writes `users/{uid}` on first sign-in, but the current rules allow
writes to that collection only for admins, so the write is rejected for every
new user. Rather than port a broken write, the rules gain a narrow `create`
clause permitting a user to create only their own document with both privilege
flags forced to `false`:

```
match /users/{uid} {
  allow read: if isOwnUser(uid) || isAdmin();
  allow create: if isOwnUser(uid)
                && request.resource.data.admin == false
                && request.resource.data.readOnlyOthers == false;
  allow update, delete: if isAdmin();
}
```

Privilege escalation stays impossible: only an admin can flip `admin` or
`readOnlyOthers` after creation.

## Data

`charactersProvider` is a `StreamProvider` over the `characters` collection,
filtered `where('email' == user.email)` unless the user is `admin` or
`readOnlyOthers`, in which case the whole collection is watched. This mirrors
`useCharacters` exactly.

`usersProvider` is a `StreamProvider` over `users`, active only for admins.
Flag updates go through `UserRepository.updateUserFlags`.

Because both are live snapshots, an admin's edit repaints every open client on
its own. The manual cache invalidation in `useCharacters` and `useUsers` has no
equivalent and is not ported.

Firestore's on-device persistence is enabled (the Android default). A cold start
renders cached characters immediately, and an edit made offline queues and syncs
on reconnect. The AppBar shows an unobtrusive offline marker driven by
`snapshots(includeMetadataChanges: true)` when the snapshot is from cache or has
pending writes.

## Theme

`app_theme.dart` holds the palette as named constants — `crimsonDeep #3A0A0A`,
`crimson #6B1A1A`, `gold #C8860A`, `parchment #E0CCAA`, `parchmentLight
#F5E8D0`, `inkDark #1A0A0A`, `bgDark #1A1008` — and a `TextTheme` pairing Cinzel
(display, headline, labels) with Libre Baskerville (body). The component
overrides in `theme.js` become `ProgressIndicatorThemeData`, `ChipThemeData`,
`ElevatedButtonThemeData` and `InputDecorationTheme`.

Gradients have no home in `ThemeData`, so the recurring ones — the crimson band,
the gold-to-crimson XP fill, the parchment card fill — are declared as constants
beside the palette. `ornaments.dart` exposes the three repeated motifs:
`OrnamentDivider` (line, ✦, line), `CornerOrnament` (❧, mirrored with
`Transform.scale(scaleX: -1)`), and `TopBand`/`BottomBand`. The character card
and the edit screen share them instead of duplicating the styling twice, as the
CSS and the dialog's inline `sx` objects currently do.

## Screens

**Login.** Dark scaffold, ⚔ mark, Cinzel title, "Kronika Bohaterów", ornament
divider, gradient sign-in button carrying the "G" glyph and the two-line label,
flavour text. A near-literal translation of `Login.module.css`.

**Home.** `AppBar` with a gradient `flexibleSpace` and a gold bottom hairline,
title `⚔ LifeRPG`, admin and logout `IconButton`s. The body is a `ListView` of
`CharacterCard`, constrained to roughly 440 logical pixels so it does not
stretch on tablets. `charactersProvider.when(...)` supplies loading and error
states; the error state is new, as the web app has no characters-error path.

No pull-to-refresh: the lists are live snapshots, so the gesture would be a
no-op dressed as a feature.

**CharacterCard.** A `Column` inside a `ClipRRect` and `Container`: top band,
then a `Stack` whose body is the bordered inner frame with `Positioned` corner
ornaments, name and class, ornament divider, level row with badge, XP block,
gold row, optional favour emoji, optional traits `Wrap` of pills, bottom band.
Tapping the XP bar toggles the "Do następnego poziomu: N XP" hint through
`AnimatedSize`, matching the current behaviour.

**EditCharacterScreen.** The main mobile-native departure: a pushed full-screen
route rather than a `Dialog`. It keeps the parchment card content but gains a
real `AppBar` (back cancels, "Zapisz" saves), a `Form` with numeric validation,
and enough room that the soft keyboard does not fight a 280-pixel dialog. Trait
names use Flutter's built-in `Autocomplete<String>`, seeded from the trait names
present across loaded characters — the same idea as the current
`existingTraitNames` memo. Save failures surface as a `SnackBar` rather than
`alert()`.

**UserManagementScreen.** Also a full route: a `ListView` of users with a
`readOnlyOthers` `Switch`, disabled for admin users, a per-row spinner while a
write is in flight, and a `SnackBar` on failure.

All Polish labels (Poziom, Złoto, Doświadczenie, Przychylność, Cechy, Zapisz,
Wyloguj, and the rest) carry over verbatim.

## Feature flag

`VITE_SHOW_FAVOUR` becomes `--dart-define=SHOW_FAVOUR=true`, read as
`const bool.fromEnvironment('SHOW_FAVOUR')`. Being compile-time, it tree-shakes
the favour UI out of the binary exactly as the Vite flag does out of the bundle.

## Tests

`flutter_test` with `fake_cloud_firestore` and `firebase_auth_mocks`, injected
through the overrides exposed by `firebase_providers.dart`.

Ported from the existing suites:

- `Character.test.jsx` → `character_card_test.dart`: renders stats, XP hint
  toggle, traits, and the edit affordance only for admins.
- `EditCharacterDialog.test.jsx` → `edit_character_screen_test.dart`: fields
  populate from the character, save writes to Firestore, traits add and remove.
- `UserManagement.test.jsx` → `user_management_screen_test.dart`: switch
  behaviour, admin rows disabled, failure surfaces an error.

New:

- `charactersProvider` scoping — own-email, admin, and `readOnlyOthers` cases.
- First-login bootstrap creates `users/{uid}` with both flags false.

## CI/CD

Both Firebase Hosting workflows are deleted and replaced:

- **`android-pr.yml`** — on pull request: `flutter analyze`, `flutter test`,
  `flutter build apk --debug`, with the APK uploaded as a build artifact so a
  preview can be installed straight off the PR. `google-services.json` comes
  from a repository secret.
- **`android-release.yml`** — on push to `master`: `flutter build appbundle
  --release`, signed from a base64-encoded keystore secret, published to
  Firebase App Distribution. This uses the same Firebase project and needs no
  Play Console setup to start delivering builds to a device.

Required secrets: `GOOGLE_SERVICES_JSON`, `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`,
`FIREBASE_SERVICE_ACCOUNT_LIFERPG_F3BAB` (already present).

## Cutover order

Each step leaves the repository in a working state.

1. `flutter create` into the repo; register the Android app in Firebase with
   debug and release SHA fingerprints; run `flutterfire configure`.
2. Add the `users/{uid}` create rule and deploy the rules.
3. Theme, ornaments, models.
4. Repositories and providers, with their tests.
5. Login, Home, CharacterCard.
6. EditCharacterScreen, then UserManagementScreen.
7. Swap the workflows; delete `src/`, `index.html`, `vite.config.js`,
   `package.json`, `package-lock.json`, `tsconfig.json`, `.eslintrc*`,
   `.prettierrc`, `.env.example`, `public/`; remove the `hosting` block from
   `firebase.json`.
8. Rewrite `CLAUDE.md` for the Flutter stack.

## Out of scope

Play Store publication, push notifications, iOS, any change to the Firestore
data model, and any new product feature.
